# Native jobs and legacy pipelines

SQLite jobs are authoritative operational records included in native backup/restore. Job IDs are library scoped. Queue creation validates the requested operation against the caller's capabilities; execution checks the worker principal again. Secrets are supplied by the operator at execution time, never persisted in job arguments. Errors stored by the worker are bounded categories without provider payloads or filesystem paths.

`llmbase --base-dir PATH --library-id ID op job_enqueue --args '{"operation":"index","args":{}}'` creates a durable job. `op job_run_one --args '{"worker_id":"runner-1"}'` claims and executes at most one ready job through Application, returns its terminal record, or returns null when none is ready. A supervisor or timer can repeat this finite command; there is no hidden daemon. `job_get`, `job_list`, `job_events`, `job_cancel`, and `job_retry` expose the ledger. Write and Private capabilities are required to execute queued work; the operation's own Read/Model/Write requirements still apply.

Claims use a random, nonserializable ownership token and a 60-second lease renewed every 10 seconds. Completion and heartbeat require the current unexpired token, so a recycled PID or previous worker cannot complete a new lease. Expiration records `interrupted`; explicit retry applies bounded exponential backoff and an attempt budget. Inline compile/promote create and claim their internal records in one SQLite transaction, preventing a general worker from stealing an intermediate queued record. Nested job-management jobs are rejected.

Cancellation stops cooperative model work and prevents queued jobs from being claimed. Accepted synchronous writes can already have committed, and cancellation does not undo them. If request cancellation arrives before an accepted operation returns successfully, the worker records `partial` with its result. A separately persisted cancellation remains `cancelled`; inspect source revisions and operation receipts for effects committed before cancellation. A process crash or lost lease cannot be reported as success; retry reuses operation-specific receipts and caches where available. Provider success before local persistence remains an unavoidable external-call crash window.

Legacy pipeline events and chunk caches retain their existing filenames and JSON formats through `compat_pipeline`. JSONL append, truncated-tail recovery, fsync, state reduction and hash-cache persistence run in Rust. Python reads live timestamp/callback overrides at each call. Stage locks retain old PID metadata for legacy consumers and add a stable kernel lease; new marked records use the kernel lease to distinguish process death from PID reuse. Force-removing metadata cannot break a live kernel lease. Distinct stages can run concurrently. These compatibility events are not falsely presented as native SQLite job events.

Verification: core `tests/worker.rs` covers real queued indexing, persistence, scope, cancellation before claim, failure records, atomic inline claims and competing workers. Existing jobs module tests cover expired leases and retry fencing. `tests/compat_pipeline.rs` and Python `tests/rust_migration/test_native_pipeline.py` cover legacy events/cache and stage behavior; candidate-wheel validation is required before these facade changes are accepted.
